# Architecture v2

## 1. Purpose
Cyberjack симулирует реакцию субъекта на воздействие и строит выразительный ответ. V2 фиксирует фактическую архитектуру после внедрения контекстов, анатомических слотов и собственного prompt-стека. Главные цели:

- жёстко изолировать ядро расчёта реакции;
- держать правила доступа/слотов вне UI, но рядом с оркестратором;
- собирать промпт из наших данных и передавать его в любой LLM (ST теперь только транспорт);
- сохранять единый источник правды в SQLite через репозитории.

## 2. Слоистая модель
| Слой | Ответственность | Основные файлы |
| --- | --- | --- |
| Interaction Engine | Нормализация входа, вычисление реакции за тик, обучение | `src/engine/*`
| Action Compiler & Context System | Сбор финального вектора действия из пресета, LLM-модификаторов и активных контекстов | `src/compiler/*`, `src/orchestration/contextManager.ts`
| Scenario & Access | Доступные действия сцены, слоты, стоимость ресурсов, переходы | `src/scenario/*`, `sceneRepo`, `sceneCharacterRepo`
| Orchestration | Загрузка состояния, запуск тика, применение команд LLM, сохранение, запуск сценария | `src/orchestration/runGameTick.ts`, `loadTickState.ts`, `saveTickState.ts`, `eventRouter.ts`
| Expression & Prompt Stack | Построение системного промпта, многоперсонажная оркестрация, вызов LLM, память | `src/prompts/*`, `src/orchestration/sceneOrchestrator.ts`, `src/services/*`, `src/adapters/*`
| Persistence | SQLite и репозитории доступа | `src/infrastructure/db.ts`, `src/infrastructure/repositories.ts`
| Interface | HTTP API + React UI, в т.ч. очередь действий и проверки слотов | `src/api/*`, `src/ui/*`

## 3. Доменные сущности
- **Subject** (`subjects`, `SubjectCoreState`): параметры чувствительности/ёмкости/открытости/пластичности/отношения + baseline.
- **SubjectPointState** (`subject_point_states`): локальная чувствительность/отношение, знакомство, счётчик экспозиции.
- **ActionPreset** (`action_presets`): базовый вектор, теги, `contextConfig` (тип, занимаемые слоты, длительность, эксклюзивность, приоритет, блокировки/баффы).
- **Inventory / Equipment**. Каждый персонаж может владеть объектами (например, “электрошокер”, “полевой набор фиксаторов”). Такие предметы дают доступ к действиям вне зависимости от сцены (или позволяют накладывать контексты). Для этого нужна таблица `character_items` (`character_id`, `item_id`, `state`, `charges`, `metadata`). Кроме того, сцена может содержать стационарные объекты (`scene_objects`: `scene_id`, `node_id`, `item_id`, `owner_id`, `metadata`) — например, “капсула сенсорной депривации” в секторе лаборатории. Сценарий использует эти данные, чтобы расширять `scene_layouts` и набор доступных действий.
- **ActiveContext** (`active_contexts`): применённые позы/состояния/экипировка. Хранит `actionId`, длительность, счётчик тиков, а также опциональный `pointId` для локальных модификаторов кожи/конечностей.
- **Scene** (`scenes`): список допустимых действий, стоимость ресурсов, правила переходов, список слотов, персонажи (`scene_characters`, поле `slot_id`).
- **PlayerState** (`players`): ресурсы, используются для списания стоимости действий.
- **Event Logs** (`event_logs`): полный след действий для диаграмм, промптов и памяти.
- **Memory** (`chat_memory`, `chat_memory_summary`, `memory_embeddings`): цепочка истории и сжатых резюме/векторных воспоминаний для long-term отзывов.
- **Memory**:
  - `memory_embeddings` — контекст для LLM (текстовые записи с эмбеддингами, как сейчас). Используются для построения промптов и аналитики (“вспомни последнюю перегрузку”).
  - `memory_facts` (как отдельной сущности больше нет) — детерминированные факты, влияющие на симуляцию (травмы, фобии, устойчивость), теперь работают через унифицированный механизм **контекстов** (`active_contexts`). Пул условных триггеров (Condition Engine) отслеживает пороговые значения (например, “capacity < 10 на протяжении 3 тиков”) и, при срабатывании, применяет контекст типа `trauma` или `phobia` через `ContextManager`, который автоматически влияет на формулу тика.

Новая сущность v2 — **анатомические слоты**. Они работают на двух уровнях:
1. UI-очередь (`src/ui/App.tsx`) не даёт добавить в один тик действия, пересекающие `occupiesPoints`.
2. `ContextManager` проверяет пересечения активных контекстов и слотов (`global_pose`, `left_hand`, `knees` и т.п.) при применении поз/состояний.

## 4. Slot & Context System

- **Базовые слои**. Анатомия и локации приходят из домена (anatomy presets, scene.slots/scene_characters.slot_id). Кроме них допускаются виртуальные слои: социальные статусы, сенсорные состояния, “одиночество”, наркотические эффекты и т.д.
- **Определения контекстов**. Каждый `ActionPreset` через `contextConfig` описывает, какие слои он занимает (`occupiesPoints`), блокирует (`blocksPoints`, `blockedFunctions`), усиливает (`boostedFunctions`), какие функции требуются (`requiredFunctions`), насколько длится и каков приоритет/эксклюзивность. Позы занимают слоты анатомии; фиксаторы и одежда занимают/блокируют слоты и могут модифицировать соседние точки (например, джинсы блокируют `anus`, ослабляют `hips`). “Фантомные” состояния (сенсорная депривация, наркотики) занимают отдельные виртуальные слои и влияют на формулы без блокировки анатомии.
- **ContextManager / Slot Engine** хранит активные контексты (`active_contexts`), решает конфликты (эксклюзивность, приоритеты), тикает длительности и отдаёт компилятору суммарные модификаторы (`compileContextVector`). Он же предоставляет API для удаления/добавления контекстов и используется сценарием, когда нужно снять/навесить фиксаторы.
- **UI очередь** и сценарий используют слоты для ранней валидации: очередь не позволяет добавить два действия, занятых одним слоем, а сценарный слой задаёт план помещения (слоты-сектора) и проверяет, можно ли совершить контактное действие между участниками.
- **Влияние на тики**. Все активные слоты автоматически влияют на каждое действие: их вектор суммируется с базовым действием, поэтому поза/одежда/фиксация/виртуальное состояние добавляют “фоновые” эффекты без участия движка.

## 5. Поток тика
1. **UI/API событие** → `POST /api/tick`. Для текста UI добавляет `textMessage`, для очереди физики — `presetId`/`intensity`.
2. **Event Router** (`eventRouter.ts`) определяет активную точку. Если пришёл текст — вызывает `parser/verbalParser.ts`, который через `adapters/llmAdapter.parseVerbalInputWithLLM` возвращает семантический вектор + команду (активировать/снять контекст, сменить позу).
3. **LoadTickState** грузит core, point, игрока, сцену, relation субъект↔калибратор.
4. **Action Compiler** объединяет пресет, ручную интенсивность, LLM-модификаторы и суммарный вектор активных контекстов (`compileContextVector`).
5. **Dynamic contexts** (`compiler/dynamicModifiers.ts`) добавляют виртуальное давление (ментальные/телесные перегрузки).
6. **runTick** вызывает `engine.computeResult` + `applyLearning`, выдаёт `TickOutput`.
7. **Context processing**:
   - команды LLM больше не принимают решения сами. Классификатор возвращает только `commandIntent` (`activate_context`, `deactivate_context`, `change_pose`, `move_to`, `perform_action` и т.д.), а `runGameTick` трактует его как инициативу субъекта: вызывает сценарный `validateAction`/`moveCharacter`, проверяет комплаенс, доступность слотов, ресурсы и при успехе применяет контекст/перемещение (иначе логирует отказ);
   - `ContextManager.processTick` тикает длительности и удаляет просроченные состояния;
   - если у действия есть `contextConfig`/`removeContexts`, это тоже применяется тут.
8. **saveTickState** сохраняет новые core/point, обновляет baseline отношения субъект↔игрок через `baselineUtils`, пишет `event_logs` (включая нарративное описание действия).
9. **Scenario step**: `runScenarioStep` пока упрощён — возвращает возможный `nextSceneId`, обновлённый игрока и прогресс миссии. Отдельно слой сценария (временно — контроллер) проверяет близость по сценическим слотам, чтобы контактные действия допускались только при совместимом расположении.
10. **Prompt**: `buildPromptPayloadWithDB` собирает срез состояния (core, point’ы, активные контексты, последние события) и передаёт в `buildPromptPayload`, который добавляет: state summary, диагностические лейблы, отношения сценических персонажей, историю чата, лонг-тёрм memory (`services/memoryLayer.selectLongTermMemory`), кастомное форматирование из `prompts/config.ts`, narrator prompt и предзаготовленные инсайты.
11. **Scene orchestrator**: `executeTurnConversations` опрашивает `orchestrateSceneActors` — решает, кто реагирует (жертва, наблюдатели, рассказчик). Для каждого актёра строится собственный промпт (наблюдатели получают state другого субъекта). Ответы генерятся через `adapters/sillyTavernAdapter` (мы используем ST backend как транспорт и JSON-валидатор, но все данные и память строим сами). Каждая реплика логируется в чат-мемори, `recordMemoryEvent` создаёт embed’ы, `chatSummary` сворачивает историю.
12. **Ответ контроллеру**: API возвращает `TickBundle`, diagnostics, prompt, LLM-ответ, чтобы UI обновил состояние.

## 6. Сценарные ограничения и слоты
- **Ответственность**. Сценарный слой должен целиком отвечать за “что разрешено в этой сцене”: список действий, план помещений (слоты/сектора), близость участников, переходы, миссии и условия по ресурсам. Сейчас часть проверок (проксимити) живёт в контроллере, но архитектурно они принадлежат scenario и постепенно будут перенесены в отдельные функции (`validateAction`, `checkProximity`, `applyResourceEffects`).
- **Доступность действий** (`scene.availableActions`). `scenario/checkActionAccess` сверяет, допускает ли сцена выбранный `presetId` (плюс глобальные исключения вроде `wait`). Когда проверка переедет в scenario слой, UI/API перестанут держать собственные списки.
- **Ресурсы**. Ресурсы должны храниться у любого персонажа, а не только у игрока. План: завести отдельное хранилище (например, `character_resources`) или расширить `characters` и научить сценарий списывать/начислять ресурсы между персонажами (переводы, награды). Функция `applyResourceCosts` станет частным случаем сценарного “трансфера” (`consume` / `grant`).
 - **Проверка условий**. Помимо списания, нужны требования “минимум N ресурса до начала”. В `scene.actionCosts` (или отдельной структуре) появятся блоки `require` и `consume`, чтобы `checkActionAccess` сначала проверял наличие, а уже потом инициировал списание. Логика проверки останется на стороне scenario, оркестратор лишь вызывает `validateAction` и действует по ответу.
- **Scene slots и layout**. `scene.slots` + `scene_characters.slot_id` описывают, кто в каком секторе находится, а `scene_layouts` хранит граф (узлы/рёбра, типы переходов, условия). Сценарий использует эти данные для правил близости (“можно ли трогать”, “в поле зрения ли персонаж”), перемещений и переходов между сценами.
+ **Персональные модификации сцен**. Персонажи (например, Калибратор) могут устанавливать оборудование, менять план помещения, “резервировать” слоты. Такие изменения отражаются в `scene_layouts`/`scene_objects`: добавление узла “капсула сенсорной депривации”, привязка действий (“поместить S-01 внутрь”), изменение доступных переходов. `validateAction` учитывает наличие предметов/объектов (через `requiresItem`, `requiresSceneObject`), а UI отображает их на карте. Сценарий валидирует, какие объекты доступны владельцу, и какие новые действия появляются для других участников.
- **Анатомические слоты**: часть `contextConfig`. UI очередь и `ContextManager` запрещают одновременные действия одной конечностью / позой. Флаг `exclusiveWithinPoint` снимает старый контекст при конфликте, `priority` позволяет «перебивать» низкоприоритетные состояния.
- **Virtual contexts**: `dynamicModifiers` добавляет скрытые эффекты (например, перегрузку участка тела) без записи в `active_contexts`.

## 7. Оркестрация
- **Event routing.** `eventRouter` принимает HTTP payload, определяет point (текст → `parser/verbalParser` → LLM классификатор), подмешивает `dynamicModifiers` и вызывает `runGameTick`.
- **Сбор состояния.** `loadTickState` вытягивает core/point/player/scene/relation через репозитории и формирует snapshot для тика. Это единственная точка входа оркестрации к данным.
- **Запуск тика (`runGameTick`).** Делает последовательность действий: проверяет сценарные ограничения (`checkActionAccess`, в будущем — `validateAction`), списывает/проверяет ресурсы, собирает историю (`eventQueries`), компилирует действие (preset + LLM‑модификаторы + `compileContextVector`), применяет `dynamicModifiers`, вызывает движок (`runTick`). После расчёта обрабатывает команды из текста (сравнивает комплаенс, вызывает `ContextManager` или пишет отказ), применяет `contextConfig` текущего пресета, тикает активные контексты, сохраняет состояние (`saveTickState`). Затем запускает `runScenarioStep` (переходы/миссии), обновляет `playerRepo`/`sceneRepo`, строит diagnostics и prompt.
- **Сохранение.** `saveTickState` фиксирует новые core/point, baseline отношения, логирует событие (включая нарратив), обновляет память отношений субъекта и игрока.
- **Коммуникация.** `sceneOrchestrator` (после `runGameTick`) решает, кто реагирует (жертва/наблюдатели/рассказчик), строит индивидуальные промпты (`buildPromptPayload`) и вызывает LLM через адаптеры. Здесь же обновляется `chatMemoryRepo`, `recordMemoryEvent`, `chatSummary`.
- **Итог.** Оркестратор возвращает `TickBundle`, diagnostics, prompt и LLM‑ответ, а также служебные данные (scenario result, metadata). Именно этот слой склеивает компилятор, движок, сценарий, prompt и persistence.

## 8. Prompt & Expression stack
Компоненты:
- `prompts/buildStateSummary.ts`, `prompts/semanticTranslator.ts` — переводят core/point статистики в соматическое описание. Используют `activeConfig.somaticSense` для уровней чувствительности/ёмкости/открытости/отношения, определяют особые состояния (паника, сабспейс, гиперэстезия), перечисляют активные слоты и ограничения на речь.
- `diagnostics/semanticActionInterpreter.ts`, `diagnostics/buildDiagnostics.ts`, `diagnostics/traitInference.ts` — превращают числовой вектор действия и результат движка в фразы “Это ощущается как…”, реакцию (“нейтральная / удовольствие / перегрузка”) и стабильные черты. Эти фразы попадают и в UI, и в промпты.
- `prompts/buildRecentEventsSummary.ts`, `prompts/buildMemoryInsights.ts` — формируют блок “последние события” и long-term инсайты из `event_logs`. При обработке используют diagnostics, чтобы описывать ощущения и рефлексы.
- `prompts/buildPromptPayload.ts` + `buildPromptPayloadWrapper.ts` — собирают финальный пакет для LLM: state summary, контексты, отношения (`characterRelationRepo`), сценические слоты, недавние события, long-term memory (`services/memoryLayer.selectLongTermMemory`), narrator prompt, конфигурацию из `prompts/config.ts`. Пока wrapper ещё читает данные напрямую из БД, но цель — кормить его готовым `TickBundle`.
- `prompts/config.ts` — единое хранилище всех текстовых шаблонов (somatic sense уровни, названия состояний, заголовки “Последних событий”, инструкции персонажу/рассказчику, пустой ввод, параметры оркестратора и настройки ST контекста). Через `updateConfig` можно менять стиль речи без правки кода.
- `prompts/openRouterPromptBuilder.ts` — из payload строит системный промпт: biography персонажа, текущая сцена, физическое состояние (`translateStateToPrompt`), список ограничений, блочные инструкции и блок “текущий тик”.
- `orchestration/sceneOrchestrator.ts` — решает, кто говорит (жертва, наблюдатели, рассказчик), добавляет narrator-реакцию и вызывает LLM. Одновременно обновляет `chatMemoryRepo`, создаёт embeddings (`services/memoryLayer.recordMemoryEvent`) и свёртки (`services/chatSummary`).
- `adapters/sillyTavernAdapter.ts` и `adapters/llmAdapter.ts` — две стратегии вызова LLM. Первая использует локальный SillyTavern backend (JSON schema, health-checkи), вторая бьёт напрямую в OpenRouter/другие модели.

## 9. API и UI
- **API** (`src/api/controllers`). REST-интерфейс для UI. Текущие маршруты:
  - `/api/state` (`stateController.getState`) — возвращает срез состояния: core/point, список точек, доступные действия сцены (включая `occupiesPoints` и стоимость), текущее расположение персонажей (`scene.characters`), отношения (`characterRelationRepo`) и ресурсы игрока. `/api/state/subject` позволяет вручную править core/baseline (debug-панель).
  - `/api/tick` (`tickController.processTick`) — главный runtime-эндпоинт. Принимает `subjectId`, `pointId`, `sceneId`, `presetId`/`textMessage`, `playerId`, флаги `skipLLM`/`skipTimeTick`, опционально `dynamicModifiers`. Возвращает `TickBundle`, diagnostics, промпт и LLM-ответ. `/api/tick/wait` запускает несколько “пустых” тиков.
  - `/api/scene/*` (`sceneController`) — управление сценами и контекстами: `getScenes`, `moveScene` (перемещение персонажа и слота), `getContexts`/`toggleContext` (ручное включение поз/фиксаторов для отладки). В идеале большая часть этой логики должна переехать в scenario layer (API только проксирует команды “переместить”, “задать слот”).
  - `/api/player/*` (`playerController`) — обновление ресурсов игрока и отношений (`updatePlayer`, `updateRelations`, `getRelations`). В дальнейших версиях эти операции будут обобщены на “любой персонаж” (персональные ресурсы).
  - `/api/meta/*` (`metaController`) — конфигурация промптов (`getConfig`/`postConfig`), генерация/просмотр профиля персонажа и выгрузка сгенерированного persona/lore (при желании — синхронизация с SillyTavern).

  **Целевое состояние:** контроллеры остаются тонкими (валидация + вызов сервисов), а вся бизнес-логика (проксимити, применение контекстов, расход ресурсов) живёт в scenario/orchestration. Ответы должны оперировать типами `TickBundle`, `SceneSnapshot`, `CharacterResourceSummary`, чтобы UI не зависел от внутренних таблиц.
- **UI**. Сейчас у нас есть один “отладочный” клиент (`src/ui/App.tsx`):
  - Console/Queue вкладка — выбор субъекта/точки/действия, текстовый ввод, очередь воздействий (с проверкой `occupiesPoints`), чат, diagnostics/prompt trace, просмотр результатов движка.
  - Config вкладка (включает `ConfigEditor`) — редактирование глобальных промпт-настроек. Нужно расширить её до полноценного “Prompt & Character Editor”: визуальный список персонажей, просмотр/редактирование профайлов (persona/history/traits), редактирование текстовых шаблонов `prompts/config.ts`, вызов генератора персонажей и применение результатов. Список персонажей должен подтягиваться из `characterRepo`/`ensureGeneratedProfile`, позволять обновлять параметры.
  - Scene/Map editor (планируется как отдельная вкладка) — управление сценами и картами: список сцен, редактирование `scene.availableActions`, `actionCosts`, `slots`, визуализация layout (когда появится `scene_layouts`), перемещение персонажей по слотам, ручное включение/отключение контекстов. Сейчас часть логики (moveScene, toggleContext) есть, но UI нужно выделить в отдельный экран с визуальной картой и инструментами редактирования.
  - Resource/Relations editors — правка core параметров, ресурсов игрока, отношений (обновление `character_relations`). В будущем эти панели должны работать с ресурсами любого персонажа (не только игрока) и учитывать сценарные `require/consume` правила.

  В продовой версии UI будет разделён: операторский (сценарист/калибратор) — включает все вышеописанные вкладки, плюс карту и редактор промптов; игрок — только Action Console/чат без доступа к настройкам. Это следует учесть при дальнейшей разработке.
  Критическое требование: API должно покрывать ВСЕ игровые и редакторские возможности, чтобы как человек, так и автономный агент (ИИ) могли полностью играть и модифицировать контент без прямого доступа к БД. Любые новые механики (слоты, ресурсы, инвентарь, сцены, память) обязаны иметь API-эндпоинт (или gRPC/WS эквивалент), иначе они не считаются реализованными.

  **Продовый (игровой) UI** — отдельный клиент с минималистичным интерфейсом:
  - Центральная панель — общий чат сцены + ответы рассказчика. Реплики персонажей всплывают и у аватаров на карте, и в общем потоке, чтобы не теряться при многоперсонажных сценах.
  - Статус игрока (ресурсы, активные контексты, кнопки “инвентарь”, “настройки”, “прокрутка времени”) — компактный блок сверху/сбоку.
  - Карта локации — граф из `scene_layouts`: узлы = сектора, на них размещены аватары. Всплывающие подсказки показывают текущую позу/контекст персонажа, изменения параметров, активные эффекты. Пример HUD:
    - Узел “Стол оператора”: `Калибратор`, активные контексты “Перчатки”, “Панель управления”.
    - Узел “Сектор B”: `S-01` + bubble “«Я… постараюсь…»”. Под узлом всплывает “Сенсорная перегрузка +12%”.
  - Фокус на персонажа открывает радиальное меню действий (краткосрочное воздействие, длительное воздействие, смена контекста/позы, запуск цепочек) + быстрый чат с этим персонажем. Пример:
    - Первый круг: `Воздействия`, `Контексты`, `Команды`, `Сериалы`, `Чат`.
    - Второй круг (например, `Воздействия`): “Мягкое поглаживание”, “Жесткий захват”, “Вручную ввести текст”. В тултипе видно стоимость/условия: “Требует ≥1 TimeBudget, Attitude > 30; consume 2 TimeBudget”.
    - Панель параметров справа показывает Sensitivity 62, Attitude 35, Capacity 48, Openness 55, Plasticity 40, активные контексты “Поза: Седло”, “Фиксация: Запястья”. Изменения (например, Attitude +3) всплывают тут же.
  - Фокус на сектор (узел) открывает контекстное меню перемещений: перейти в соседний сектор, взаимодействовать с объектом, перейти в другую локацию (если это граница). Можно открыть карточку сектора (описание, доступные действия).
  - Общий чат показывает события всей сцены. Примеры строк:
    - `Рассказчик: Левая ладонь дрожит, когда ремень рассекает воздух.`
    - `S-01: «…я… продолжу… дышать, как ты сказал…»`
    - `Калибратор: «Сфокусируйся на моем голосе.»`
    - `Система: Сенсорная перегрузка +12% / Дискомфорт −5%`
    - `Сцена (Лаборатория): Грави-платформа активирована.`
    Реплика NPC дублируется в bubble возле его аватара, чтобы игрок видел, кто говорит.
  - Чат с конкретным персонажем: радиальное меню имеет пункт “Чат” → открывается отдельный input. Если NPC говорит без фокуса, его bubble появляется у аватара и в общем чате. Можно фильтровать чат “только S-01”, “все + система”.
  - Уведомления/изменения параметров всплывают кратко (тултипы возле аватаров и беглая запись в общий лог). Все подробности доступны в отдельном журнале/overlay.
  - Все расширенные панели (инвентарь, журнал, настройки промптов) прячутся в отдельные overlay/иконки, чтобы основной экран оставался чистым.

  На основе этой концепции далее можно строить дизайн-систему: отдельные компоненты для чата, радиального меню, графа локаций, всплывающих уведомлений и т.д.

## 10. Persistence & Repositories
`src/infrastructure/db.ts` поднимает таблицы, мигрирует новые колонки и задаёт дефолты baseline. `repositories.ts` даёт типизированный доступ к:
- `subjectRepo`, `pointStateRepo` — чтение/запись core и точки;
- `playerRepo`, `presetRepo`, `sceneRepo`, `sceneCharacterRepo` — конфигурация доступных действий и слотов;
- `activeContextsRepo` — добавление/удаление/тикование контекстов;
- `eventLogRepo`, `eventQueries` — аналитика действий для промптов/истории;
- `characterRepo`/`characterRelationRepo` — связи между персонажами и текущие сцены;
- `chatMemoryRepo`, `chatSummaryRepo`, `memoryRepo` — память и эмбеддинги.

### 10.1 Основные таблицы SQLite
- **players** — `{ id TEXT PK, resources TEXT(JSON) }`.
- **characters** — `{ id PK, name, kind('subject'|'player'|'npc'), subject_id?, player_id?, current_scene_id?, profile_json }`.
- **character_resources** — `{ character_id, resource_key, amount, max_amount?, regen_rate?, metadata? }` — ресурсы икап/регены для любого персонажа. Сценарий использует их для `require/consume`, передач и ограничений.
- **character_items** — `{ character_id, item_id, state?, charges?, metadata? }` — персональные предметы/оборудование (шокер, набор фиксаторов). Используются в `requiresItem`.
- **scene_objects** — `{ id, scene_id, node_id, item_id, owner_id?, state?, metadata? }` — стационарные объекты сцены (капсула, станок). Используются в `requiresSceneObject`.
- **character_relations** — `{ from_id, to_id, knows, present, can_interact, attitude, baseline_attitude }` с индексом по `from_id`; используется для UI отношений и prompt’ов.
- **subjects** — `{ id PK, name, sensitivity, capacity, openness, plasticity, attitude, baseline_* }`.
- **subject_point_states** — `{ subject_id, point_id, local_sensitivity, local_attitude, familiarity, exposure_count, baseline_local_* }`.
- **action_presets** — `{ id PK, label, values_json, type, tags, context_config_json }`.
- **point_presets** — `{ id PK, label, values_json, parent_id, provides_functions, tags }` (иерархия анатомии).
- **active_contexts** — `{ id PK, subject_id, action_id, duration, ticks_active, point_id }` — источник для ContextManager.
- **scenes** — `{ id PK, available_actions JSON, action_costs JSON, transitions JSON, description, slots JSON }`.
- **scene_characters** — `{ scene_id, character_id, role, can_act, presence_state, slot_id }` — связывает персонажей со сценой и их позициями.
- **scene_layouts** — `{ scene_id PK, layout_json TEXT }` — граф плана помещения. `layout_json` содержит `nodes` (идентификатор, подписи, тип слота, произвольные свойства) и `edges` (парные связи/проходы с типами), а также опциональные правила (например, “доступ только с ключом”, “перегородка закрыта”). `scenes.slots` и `scene_characters.slot_id` должны ссылаться на `nodes.id`, чтобы сценарий мог проверять соседство и перемещения по карте.
- **event_logs** — `{ id AUTOINC, subject_id, timestamp, action_type, action_payload JSON, result_payload JSON }`.
- **chat_memory** — история коммуникации `{ id, subject_id, role, content, created_at }`.
- **chat_memory_summary** — консолидация окна сообщений `{ summary_text, important_events, start_message_id, end_message_id }`.
- **memory_embeddings** — `{ id, subject_id, text, tags, related_subjects, type, embedding JSON, metadata JSON }` — long-term память для промптов.
- **state_triggers** (ранее facts) — `{ id, subject_id, trigger_id, active_ticks }` — монитор условий, который при достижении порога автоматически накладывает контексты (например, травмы).


## 11. Отличия от v1 и дальнейшие шаги
- Prompt stack теперь полностью наш: ST больше не хранит state, только отдаёт JSON-ответы. Это отражено в `prompts/*` и `adapters/*`.
- Контекстная система (позы, restraints, экипировка) стала центральной: действия часто включают `contextConfig`, длительность и правила авто-снятия/применения.
- Слоты добавлены и в сцены (пространство), и в контексты (анатомия). Они влияют на доступность действий в UI, контроллере и ContextManager.
- Scenario слой пока минимальный. Планируемые улучшения: перенести proximity-check и доступность слотов из контроллера в `scenario/*`, расширить `runScenarioStep` (миссии/фракции), формализовать правила combo-мемори.
- Persistence содержит историю/память, что позволяет строить промпты без внешних сервисов. Следующее — вынести `buildPromptPayloadWithDB` в отдельный orchestrator-сервис, чтобы промпт собирался из уже загруженного `TickBundle`.
- API должен стать основным интерфейсом для людей и ИИ: всех игровых действий (перемещения, контексты, действия, ресурсы) и редакторских операций (сцены, предметы, память, промпты) не должно быть “скрытых” функций — всё через API.
- Требуются автотесты (интеграционные сценарии), которые запускают полную симуляцию автономного взаимодействия нескольких персонажей: по сценариям “игрок ↔ NPC”, “NPC ↔ NPC” и т.п., чтобы гарантировать, что оркестратор, сценарий и API работают end-to-end. Отладочный UI и ИИ-агенты должны опираться на те же тесты.

Эта версия архитектуры должна служить источником правды для текущей реализации и опорой для дальнейшего рефакторинга слоёв (особенно scenario и API).
